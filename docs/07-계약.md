# 계약 식별 — 불변식(INV-*) · 에러 계약(E-*) (Discovery 산출물 ③)

- 근거: [06-PRD.md](06-PRD.md) §4 개념 모델 · §5 기능 요구사항
- 방식: **DbC** — 사전조건(precondition) / 사후조건(postcondition) / 불변식(invariant)
- 표현: **Guard 함수 + 커스텀 Error 클래스**. 위반 시 `E-*` 코드를 가진 도메인 에러를 던진다
- 트랙: **Entity 트랙**(순수 도메인 — Entity + Control 유스케이스) / **Boundary 트랙**(UI · 저장소 · I/O)

> 원칙: **계약 ID 1개 = 테스트 1개 이상.** 계약에 없는 동작은 구현하지 않는다.

## 0. 타입 어휘 (계약 서술용)

```
Domain       = '국어' | '수학' | '과학·탐구' | '영어' | '사회·인성' | '예체능' | '건강·안전'
Nature       = '필수' | '자체목표' | '자유'      // ⚠️ 저장하지 않는다. 파생값 (§2-B)
Track        = '학원' | '집'
Owner        = '엄마' | '아빠'
Coverage     = '아직아님' | '비어있음' | '하는중' | '연결필요' | '기준밖'
StandardOrigin = '공교육' | '해석' | '자체'
Cadence      = { kind: '매일' }
             | { kind: '주N회', times: number }
             | { kind: '요일지정', weekdays: Weekday[] }
             | { kind: '비정기' }
YearMonth    = 'YYYY-MM'
Period       = { start: YearMonth, end: YearMonth }   // 양끝 포함
OffsetMonths = 0 | 12 | 24
```

**공교육 기준 없는 영역(NO_PUBLIC_STANDARD) = `['영어']`**
공교육 영어는 초3(2030-03) 시작이므로 취학 전 기준이 존재하지 않는다.

### StandardOrigin — 기준의 출신 (사용자 결정 2026-08-21)

> *"기준이 없는 경우에는 자체적으로 기준을 설정할 수 있도록 하자."*

| origin | 의미 | source | 오프셋 적용 |
|---|---|---|---|
| **`공교육`** | 교육과정 문서 원문 (🟦) | **필수** | ✅ |
| **`해석`** | 공교육 기준을 우리 상황에 적용한 판단 (🟨) | 권장 | ✅ |
| **`자체`** | 공교육 기준이 없는 영역에 **우리가 세운 목표** | 불필요 | ❌ |

**`자체` 기준에 오프셋을 적용하지 않는 이유**: 오프셋은 *"공교육 기준선 대비 얼마나 앞설까"* 를 뜻한다.
자체 기준은 **이미 우리가 시기까지 정한 것**이므로 뺄 기준선이 없다. 이중 조정이 된다.

> 이 결정으로 **영어도 목표를 가질 수 있게 된다.** 커버리지 판정(§3)이 근본적으로 달라진다.

## 1. PaceOffset — 선행 오프셋 (F3)

### 불변식

| ID | 불변식 | 근거 |
|---|---|---|
| **INV-PACE-01** | `months`는 `0 \| 12 \| 24` 중 하나여야 한다 | PRD §4.4. 임의 개월수는 "적기/1년/2년" 선택지를 흐린다 |
| **INV-PACE-02** | **`origin === '자체'` 인 기준에는 오프셋이 적용되지 않는다** | 자체 기준은 시기까지 우리가 정한 것. 오프셋을 얹으면 이중 조정이 된다 |
| **INV-PACE-03** | 모든 영역은 오프셋을 정확히 **0개 또는 1개** 가진다 (중복 불가) | |
| **INV-PACE-04** | 오프셋이 설정되지 않은 영역의 실효값은 **0** 이다 | 기본은 공교육 기준 그대로 |

### 에러 계약

| 코드 | 발생 조건 | 메시지 의도 |
|---|---|---|
| `E-PACE-INVALID-MONTHS` | INV-PACE-01 위반 | "오프셋은 0/12/24개월만 가능합니다" |
| `E-PACE-NOT-APPLICABLE` | `origin === '자체'` 기준에 오프셋 적용 시도 | "직접 세운 목표에는 선행 오프셋이 적용되지 않습니다" |

### 핵심 연산 계약

```
setPaceOffset(domain: Domain, months: number): PaceOffset
  requires  months ∈ {0, 12, 24}                 → E-PACE-INVALID-MONTHS
  ensures   result.domain === domain
  ensures   result.months === months
```

```
resolveTargetPeriod(standard: Standard, offsetMonths: OffsetMonths): Period
  requires  offsetMonths ∈ {0, 12, 24}           → E-PACE-INVALID-MONTHS
  ensures   standard.origin === '자체' → result === standard.baselinePeriod   (INV-PACE-02)
  ensures   standard.origin ≠ '자체' →
              result.start === standard.baselinePeriod.start − offsetMonths
            ∧ result.end   === standard.baselinePeriod.end   − offsetMonths
  ensures   result.start <= result.end                          (INV-PERIOD-01)
  ensures   offsetMonths === 0 → result === standard.baselinePeriod
```

| ID | 불변식 |
|---|---|
| **INV-PERIOD-01** | `Period.start <= Period.end` 를 항상 만족한다 |
| **INV-PERIOD-02** | 오프셋 적용은 **구간 길이를 보존한다** (start와 end를 같은 폭으로 이동) |

> **INV-PERIOD-02가 중요하다.** 오프셋은 "시기를 당기는 것"이지 "기간을 늘리는 것"이 아니다.

### 안전장치 계약 (PRD §4.4)

```
assessOffsetRaise(current: OffsetMonths, next: OffsetMonths): OffsetWarning | null
  ensures   next > current  → 경고를 반환한다                    (INV-PACE-05)
  ensures   next <= current → null 을 반환한다
```

| ID | 불변식 | 근거 |
|---|---|---|
| **INV-PACE-05** | 오프셋 **상향 시 반드시 경고를 반환**한다. 무음 상향은 불가 | 없으면 이 앱은 적기교육 도구가 아니라 **선행 압박 도구**가 된다 |
| **INV-PACE-06** | `currentTargets` 는 **누적 모델**이다. 오프셋을 올릴수록 목표가 **늘어난다**(줄지 않는다) | 설계 정정 ⑤ 참조 |

### ⚠️ 설계 정정 ⑤ (2026-08-22) — 누적 모델

> 사용자 지적: *"6살껄 하면서 7살껄 미리 하는 게 선행인데, 1년 누르면 할 게 없다는 게 말이 안 된다."*

초판 `currentTargets` 는 목표 구간을 통째로 과거로 밀어(`resolveTargetPeriod`) **지금 목표를 없앴다.**
그래서 선행할수록 목표가 **줄었고**, 결국 0이 되면 `기준밖`(옛 `초과`)으로 잘못 떴다.

**누적 규칙**: 목표는 아래 두 조건을 모두 만족하면 "지금 목표"다.
- 가속 지평(`now + offset`)까지 **이미 시작**됐다 — `baselinePeriod.start ≤ now + offset`
- 실제 현재 기준으로 **아직 안 끝났다** — `baselinePeriod.end ≥ now`

→ 오프셋 0=지금 것만, 1년=지금+1년치, 2년=지금+2년치. **바꿔치기가 아니라 더하기.**

> 오프셋 버튼 라벨도 이때 `기준/1년/2년` → **`적기`/`1년 선행`/`2년 선행`** 으로 바꿨다.
> 커버리지 상태 이름도 바꿨다: `대기`→`아직아님`, `공백`→`비어있음`, `적기`→`하는중`,
> `보완필요`→`연결필요`, `초과`→`기준밖`. (nature 의 `필수`/`자체목표`/`자유` 와 문맥이 갈린다)

## 2. Activity — 활동 (F2)

### ⚠️ 설계 정정 ② (2026-08-21) — `nature`를 입력값에서 파생값으로

초안은 활동 생성 시 `nature`(`하는중`/`플러스`)를 **사용자가 직접 고르는 필드**로 두었다.

> 사용자 지적: *"플러스 의미가 뭔데? 플러스만 있으면 왜 보완필요에 들어가?"*

`플러스`가 **두 가지를 동시에** 뜻하고 있었다.

1. 목표를 겨냥하지 않는다 (구조적 사실)
2. 못 해도 괜찮다 (심리적 처리 · C-6)

공교육 기준이 없던 시절엔 둘이 같이 갔지만, **자체 기준을 허용하면서 갈라졌다.**
→ §3에서 커버리지를 고치며 세운 원칙(*하나의 필드가 두 질문에 답하려 하면 갈 곳 없는 상태가 생긴다*)을
   `nature`에는 적용하지 않은 결과다. **같은 종류의 오류를 두 번 냈다.**

**해결**: 사용자는 **"이 활동이 겨냥하는 목표"만 선택**한다(생략 가능). `nature`는 거기서 파생된다.

### 2-A. Activity 불변식

| ID | 불변식 | 근거 |
|---|---|---|
| **INV-ACT-01** | `name`은 공백이 아니어야 한다 | |
| **INV-ACT-02** | **`nature`는 저장되지 않는다.** Activity에 `nature` 필드가 존재하지 않는다 | 파생값을 저장하면 목표 변경 시 즉시 어긋난다 |
| **INV-ACT-03** | `cadence.kind === '요일지정'` 이면 `weekdays`가 비어있지 않다 | 아무 날도 아닌 일정은 존재할 수 없다 |
| **INV-ACT-04** | `cadence.kind === '주N회'` 이면 `1 <= times <= 7` | |
| **INV-ACT-05** | `owner`는 **표시 전용**이다. 어떤 연산도 `owner`를 근거로 알림·요구·할당을 생성하지 않는다 | **OOS-1.** 위반 시 X-4 |
| **INV-ACT-06** | `targetIds`의 각 항목은 **존재하는 Standard**를 가리켜야 한다 | |
| **INV-ACT-07** | `targetIds`가 가리키는 Standard의 `domain`은 **활동의 `domain`과 같아야** 한다 | 국어 활동이 수학 목표를 겨냥할 수 없다 |
| **INV-ACT-08** | `targetIds`는 **비어 있을 수 있다** (0개 허용) | 목표 없이 하는 활동을 막지 않는다. 막으면 입력이 무거워진다 (C-3) |
| **INV-ACT-09** | `rename` 은 INV-ACT-01(공백 금지)을 지킨다. `id`·`domain`·`targetIds`·`active` 는 보존한다 | 이름만 바꾼다. 지난 기록·겨냥이 어긋나면 안 된다 |
| **INV-ACT-10** | `reschedule` 은 INV-ACT-03/04(주기 유효성)를 지킨다. 나머지는 보존한다 | 주기만 바꾼다 |
| **INV-ACT-11** | `rename`·`reschedule`·`retarget` 은 **`domain` 을 바꾸지 않는다** | 영역이 바뀌면 겨냥 목표가 다른 영역을 가리키게 된다. 영역 변경은 새 활동으로 |

### 에러 계약

| 코드 | 발생 조건 |
|---|---|
| `E-ACT-EMPTY-NAME` | INV-ACT-01 위반 |
| `E-ACT-EMPTY-WEEKDAYS` | INV-ACT-03 위반 |
| `E-ACT-INVALID-TIMES` | INV-ACT-04 위반 |
| `E-ACT-TARGET-NOT-FOUND` | INV-ACT-06 위반 |
| `E-ACT-TARGET-DOMAIN-MISMATCH` | INV-ACT-07 위반 |
| `E-ACT-NOT-FOUND` | 존재하지 않는 activityId 참조 |

### 핵심 연산 계약

```
createActivity(input: ActivityInput, standards: Standard[]): Activity
  requires  input.name.trim() !== ''                           → E-ACT-EMPTY-NAME
  requires  cadence 유효성 (INV-ACT-03, 04)                     → E-ACT-EMPTY-WEEKDAYS / E-ACT-INVALID-TIMES
  requires  ∀ t ∈ input.targetIds : ∃ s ∈ standards, s.id === t → E-ACT-TARGET-NOT-FOUND
  requires  ∀ t ∈ input.targetIds : standardOf(t).domain === input.domain
                                                                → E-ACT-TARGET-DOMAIN-MISMATCH
  ensures   result.active === true
  ensures   'nature' ∉ keys(result)                             (INV-ACT-02)
  ensures   result.id 는 고유하다
```

> **INV-ACT-05는 테스트로 증명하기 까다롭다.**
> 방법: 도메인 계층에 알림·할당을 생성하는 함수 자체를 **두지 않는다**(구조적 보장).
> 아키텍처 테스트로 "도메인 모듈이 notification/assignment 심볼을 export하지 않는다"를 검증한다.

### 2-B. Nature — 파생 규칙 (신규)

```
deriveNature(activity, standards): Nature

  linked := standards.filter(s => activity.targetIds.includes(s.id))

  if linked.isEmpty:                                    return '자유'
  if linked.any(s => s.origin ∈ {'공교육','해석'}):     return '필수'
                                                        return '자체목표'
```

| ID | 불변식 | 근거 |
|---|---|---|
| **INV-NAT-01** | 결과는 항상 `필수` \| `자체목표` \| `자유` 중 하나다 | |
| **INV-NAT-02** | `targetIds`가 비어 있으면 반드시 `자유` 다 | |
| **INV-NAT-03** | 공교육/해석 기준이 하나라도 연결되면 `필수` 다 (자체 기준과 섞여 있어도 `필수` 우선) | 공교육 대응이 더 강한 사실이다 |
| **INV-NAT-04** | **`deriveNature`는 순수 함수다.** 같은 입력 → 항상 같은 출력 | 저장하지 않으므로 매번 계산된다 |

### C-6(죄책감 금지)의 적용 지점

| nature | 미완료 시 UI |
|---|---|
| **`필수`** | 명확히 표시한다 (공교육 기준 대응 — 누적되면 문제) |
| **`자체목표`** | **중립 표시.** 우리가 정한 목표는 우리가 조정할 수 있다 |
| **`자유`** | **중립 표시.** 경고색 금지 |

| ID | 불변식 | 근거 |
|---|---|---|
| **INV-NAT-05** | `자체목표`·`자유`의 미완료는 **경고색으로 표시하지 않는다** | **C-6.** 위반 시 X-3 |

## 2-C. Achievement · OffsetGate — 달성 기반 선행 잠금 (F3) ⭐

> 사용자 결정(2026-08-22): *"현재 기준의 목표를 전부 만족해야 그다음 1년 선행이 가능하다.
>  오프셋 0 기준으로 목표를 달성했는지 보고, 달성했으면 1년 선행이 가능하다."*
>
> 이것이 선행 압박을 **구조적으로** 막는다. 오프셋이 자유 다이얼이 아니라 **아이가 해내야 열리는 문**이 된다.

### Achievement — 달성은 Completion 과 다르다

| | Completion (매일 체크) | Achievement (달성) |
|---|---|---|
| 질문 | "오늘 했나?" | "아이가 **할 수 있게 됐나?**" |
| 성격 | 날짜별. 매일 리셋 | **durable. 한 번 되면 유지** |
| 누가 | 하루 일과 | 부모가 관찰해 판단 |
| 표현 | 체크박스 | **"우리 아이 이거 돼요"** (능력. 성적 아님) |

- 데이터: 달성한 `StandardId` 목록 (`readonly StandardId[]`).
- ⚠️ **C-6**: "달성/미달성"이 아이 성적표가 되면 안 된다. **능력 서술("됨")** 로 표현하고 점수화하지 않는다.

### 불변식

| ID | 불변식 | 근거 |
|---|---|---|
| **INV-GATE-01** | `적기(0)` 는 언제나 선택 가능하다 (기준선) | |
| **INV-GATE-02** | **하향은 언제나 가능하다.** 게이트는 상향에만 건다 | 되돌아갈 자유 (INV-PACE-05와 짝) |
| **INV-GATE-03** | `targetOffset` 을 열려면 **그 아래 단계의 현재 목표를 전부 달성**해야 한다 | 사용자 결정 |
| **INV-GATE-04** | 달성 판정은 **Completion 이 아니라 Achievement** 를 본다 | 매일 체크로 선행을 열면 하루치로 오해된다 |
| **INV-GATE-05** | 아래 단계 목표가 **0개면 상향은 허용**된다 (달성할 게 없다) | 공백 진공에서 막지 않는다 |

### 연산 계약

```
requiredForOffset(domain, targetOffset, standards, now): Standard[]
  ensures targetOffset === 0 → []                                    (INV-GATE-01)
  ensures targetOffset === 12 → 이 영역의 currentTargets(offset 0)
  ensures targetOffset === 24 → 이 영역의 currentTargets(offset 12)

offsetGate(domain, targetOffset, standards, achieved, now): { allowed, required, unmet }
  ensures unmet = required.filter(t => t.id ∉ achieved)
  ensures allowed = unmet.isEmpty                                    (INV-GATE-03)
```

## 9. Pet · Care — 벌 없는 돌봄 (오늘 화면)

> 사용자 아이디어: 완료할 때마다 돌봄 버튼(먹이/쓰다듬기/놀아주기)이 열리고,
> 아이가 눌러 돌보면 펫이 자란다. **밥 못 줘서 굶는 버전이 아니다.**

### 토큰 경제

## 3. DomainCoverage — 영역 커버리지 (F3 · P-6) ⭐

> **이 앱을 만드는 이유.** *"모든 영역에서 다 하고 있는지 확인하고 싶어서 정리하는 것"*

### ⚠️ 설계 정정 (2026-08-21)

초안은 3분류(`비어있음`/`하는중`/`기준밖`)였고, **`플러스` 활동만 있는 영역을 `비어있음`으로 판정**했다.

> 사용자 지적: *"플러스인데 왜 공백이야?"*

**타당한 지적이며 초안이 틀렸다.** 3분류가 서로 **독립된 두 질문을 하나로 접었기** 때문이다.

- Q1. 이 영역에 **뭔가 하고 있는가?** (활동 유무)
- Q2. 지금 목표를 **덮고 있는가?** (목표 대응)

`플러스`만 있는 영역은 **Q1은 예 / Q2는 아니오** 인데, 3분류에 그 칸이 없어서 `비어있음`으로 밀려났다.
활동이 있는데 "공백"이라 부르는 것은 이름부터 모순이다. → **`연결필요`를 4번째 상태로 분리한다.**

### 판정 규칙 (개정)

```
evaluateCoverage(domain, currentTargets, activities): Coverage

  active := activities.filter(a => a.domain === domain ∧ a.active)
  targetIdSet := currentTargets.map(t => t.id)

  if active.isEmpty:
      return currentTargets.isEmpty ? '대기' : '공백'
  if currentTargets.isEmpty:                                  return '초과'
  if active.any(a => a.targetIds ∩ targetIdSet ≠ ∅):          return '적기'
                                                              return '보완필요'
```

> **판정이 `nature`가 아니라 `targetIds`에 직접 걸린다.**
> 사용자가 붙인 라벨이 아니라 **실제 연결 관계**로 판정하므로, 판정이 추측이 아니라 사실이 된다.

### ⚠️ 설계 정정 ④ (2026-08-22) — `아직아님` 추가

> 사용자 질문: *"오프셋이 0이라서 지금 목표 시기가 아닌 거면 첫 화면에서는 표시가 안 되는 거야?"*

4분류에서는 **목표 시기가 아직 아닌 영역**과 **시기인데 비어 있는 영역**이 둘 다 `비어있음`이었다.
전자는 정상 상태인데 "빠뜨렸다"로 읽힌다 → **C-6 위반 / X-3**.

**이건 UI 문제가 아니라 도메인 판단이다.** "지금이 이 목표의 시기인가"는 오프셋과 기준 시기로
계산되는 사실이고, 색을 칠하기 전에 이미 정해져 있다. → `아직아님` 를 5번째 상태로 분리한다.

| 상태 | 목표 | 활동 | 겨냥 | 뜻 | 필요한 조치 |
|---|---|---|---|---|---|
| **`아직아님`** | 0 | 0 | — | **아직 시기가 아니다** | **없음. 빠뜨린 게 아니다** |
| **`비어있음`** | O | 0 | — | 시기인데 비었다 | 활동을 만들거나 "안 해도 됨" 판단 |
| **`기준밖`** | 0 | O | — | 왜 하는지 정리가 안 됐다 | 자체 기준을 세우면 해소 |
| **`연결필요`** | O | O | ✗ | 하고는 있는데 목표는 안 덮인다 | 활동을 목표에 연결 |
| **`하는중`** | O | O | ✓ | 그대로 두면 된다 | 없음 |

### 불변식 (개정)

## 6. Standard — 공교육 기준 (F3)

### ⚠️ 설계 정정 ③ (2026-08-22) — 원문 대조 후

원문을 확보해 대조한 결과 **초안 계약이 너무 느슨했다.**

초안의 `INV-STD-03`은 `source.trim() !== ''` 만 요구했다.
*"2022 개정 교육과정 1~2학년군 국어"* 같은 문자열도 통과한다. **아무도 원문을 찾아갈 수 없다.**
`source` 를 구조화하고 계약을 조인다.

또 하나 — **2022 개정은 "학년군" 단위라 "1학년에 무엇을 배운다"가 교육과정에 존재하지 않는다.**
`[2국04-01]` 의 기준 시기는 **초2 말**이지 초1이 아니다. 이걸 데이터에 반영해야 한다.

### 5-A. StandardSource — 출처 구조화

```
StandardSource = {
  document: string      // '교육부 고시 제2022-33호 [별책 5] 국어과 교육과정'
  code?:    string      // '2국04-01'
  url?:     string
}
```

### 5-B. 세 가지 origin 의 역할이 갈린다 ⭐

| origin | 역할 | baselinePeriod | 목표 판정 대상 | 오프셋 |
|---|---|---|---|---|
| **`공교육`** | **근거 표시용.** 원문 인용 | **학년군 말** (예: 초1~2군 → `2028-03 ~ 2030-02`) | ❌ **아니다** | — |
| **`해석`** | **실제로 겨냥하는 목표.** 04 문서의 시기별 배치 | 우리가 배치한 구간 | ✅ | ✅ |
| **`자체`** | 공교육 기준이 없는 영역의 우리 목표 | 우리가 정한 시기 | ✅ | ❌ |

> **왜 `공교육`을 목표 판정에서 빼는가**
> 학년군 기준(`2028-03 ~ 2030-02`)은 구간이 2년이라 "지금 우리 목표"로 쓰기엔 너무 넓다.
> 원문은 **근거로 보여주는 것**이고, 실제 겨냥은 그것을 시기별로 쪼갠 `해석`이 한다.
> 이렇게 나누면 🟦(사실)과 🟨(판단)이 **데이터 구조에서도 분리**된다.

### 불변식

| ID | 불변식 | 근거 |
|---|---|---|
| **INV-STD-01** | `statement`는 **관찰 가능한 행동 문장**이다 | 04 문서 설계 원칙 |
| **INV-STD-02** | `origin`은 `공교육` \| `해석` \| `자체` 중 하나이며 반드시 명시된다 | 🟦/🟨 구분 |
| **INV-STD-03** | `origin === '공교육'` 이면 `source.document` 가 비어 있을 수 없다 | 출처 없는 "국가 기준"은 또 하나의 카더라다 |
| **INV-STD-03b** | `origin === '공교육'` 이면 **`code` 또는 `url` 중 최소 하나**가 있어야 한다 | 문서명만으로는 원문에 도달할 수 없다 |
| **INV-STD-04** | `origin === '자체'` 는 공교육 기준이 없는 영역에서도 생성할 수 있고, `source` 가 없어도 된다 | 사용자 결정 ① |
| **INV-STD-05** | `origin === '자체'` 인 기준은 **`공교육`으로 표시되지 않는다** | 우리 판단이 국가 기준으로 둔갑하면 P-3를 앱 안에서 재생산한다 |
| **INV-STD-06** | **`origin === '공교육'` 인 기준은 `currentTargets` 에 포함되지 않는다** | 근거 표시용이지 목표가 아니다 |
| **INV-STD-07** | `origin === '해석'` 은 `refines` 로 근거가 되는 `공교육` 기준을 가리킬 수 있다 (선택) | 🟨가 어느 🟦에서 나왔는지 추적 |
| **INV-STD-08** | `refines` 가 있으면 그 대상은 **존재하는 `origin==='공교육'` 기준**이어야 한다 | |

## 11. 출처 (Provenance) — "이거 공교육 기준 맞아?" ⭐

사용자 피드백 ④: *"공교육 기준으로 나오는 건지 모르겠다. 표시가 되면 좋겠다."*
목표마다 출처를 배지로 드러낸다. 신뢰의 근거이자, 이 앱의 핵심 가치다.

`provenanceOf(standard, all)` 는 기준 하나의 출처를 판정한다 (순수 함수):

| 코드 | 계약 | 왜 |
|---|---|---|
| **INV-PROV-01** | `origin='공교육'` → `{kind:'공교육', doc}`. doc 은 source.document 에 '누리과정'이 들어가면 `누리과정`, 아니면 `성취기준` | 근거 문서를 사람 말로 |
| **INV-PROV-02** | `origin='해석'` → `refines` 가 가리키는 공교육 기준의 문서로 귀속한다 (INV-STD-07/08). 활동은 해석을 겨냥하지만 배지는 그 근거인 공교육을 보여준다 | 해석은 공교육의 대리물 |
| **INV-PROV-03** | `origin='자체'`, 또는 refines 없는 해석 → `{kind:'자체'}` | 공교육 밖 목표는 정직하게 자체로 |

**표시 규칙 (오늘·현황):** 활동이 여러 목표를 겨냥하면 **공교육 근거 목표를 대표(첫째)로** 정렬한다
(`Task.targets` 는 이미 정렬돼 온다). 오늘 화면은 대표 + "외 N개"로 요약하고, 전체 매핑은 현황 탭이 맡는다.

### 8.1 저장·동기화 계약 (회사↔집 C-4)

`App`은 어느 어댑터인지 모른다 — 오직 `AppStore` 포트(비동기 `load`/`save`, 선택적 `pull`)만 본다.
그래서 로컬↔Supabase 전환에 App 코드가 한 줄도 안 바뀐다.

| 코드 | 계약 | 왜 |
|---|---|---|
| **INV-STORE-01** | 어댑터의 `load`/`save`/`pull`은 **절대 던지지 않는다.** 실패는 `null`(load/pull)·무음(save) | 저장 실패로 앱이 죽으면 안 된다. 사생활 모드·오프라인·4xx/5xx 모두 견딘다 |
| **INV-STORE-02** | `SyncStore.save`는 **로컬을 먼저 저장**하고 원격은 best-effort. 원격 실패가 로컬 저장을 막지 않는다 | 로컬이 항상 진실의 근거. 네트워크는 공유 채널일 뿐 |
| **INV-STORE-03** | 원격 `load`/`pull` 실패가 **로컬 데이터를 절대 지우지 않는다** | 일시적 네트워크 오류로 seed 로 되돌아가면 데이터 유실 |
| **INV-STORE-04** | 버전(`SNAPSHOT_VERSION`) 불일치 스냅샷은 무시하고 `null` (로컬·원격 동일 규칙) | 낡은 구조로 앱을 깨뜨리지 않는다 |
| **INV-STORE-05** | 저장 이펙트는 직전 직렬화본과 **같으면 저장하지 않는다** | 원격에서 당겨온 걸 곧바로 도로 저장해 원격을 덮는 되먹임을 막는다 |

**동기화 모델:** 스냅샷 통째 last-write-wins. 기기 전환(회사→집)은 앱이 다시 보일 때
`pull()`로 최신 공유본을 당겨 해결한다. 두 기기에서 동시에 편집하면 나중에 저장한 쪽이 이긴다
(가족 2인·저빈도라 허용). 실시간 병합이 필요해지면 Supabase Realtime 으로 확장하되 포트는 그대로다.

### ②·④에서 배운 것 — 이후 설계에 적용할 원칙

> **하나의 필드가 두 개의 독립된 질문에 답하려 하면 반드시 갈 곳 없는 상태가 생긴다.**
> 새 분류를 만들 때는 먼저 **몇 개의 질문에 답하는 축인지**부터 센다.

**같은 오류를 두 번 냈다.**

| | 필드 | 섞인 두 질문 | 증상 |
|---|---|---|---|
| ② | `Coverage` | ①뭔가 하고 있는가 ②목표를 덮는가 | `플러스`만 있는 영역이 `비어있음`으로 밀림 |
| ④ | `nature` | ①목표를 겨냥하는가 ②못 해도 괜찮은가 | 자체 기준 도입 후 `플러스` 정의가 붕괴 |

→ **해소 방법도 같다: 축을 분리한다.** ②는 상태를 4개로 나눴고, ④는 저장값(`targetIds`)과 표시값(`nature`)을 나눴다.
